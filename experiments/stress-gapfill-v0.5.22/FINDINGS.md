# 压力测试补齐（2026-10-28）

第一轮压力测试（`stress-qwen3-8b-v0.5.22/`、`stress-qwen38-27b-v0.5.22/`）只覆盖了 W2 共享前缀和 w1-natural 自然对话。报告大纲里的四个场景和三个模型还缺这几块：

- **多轮对话（append）**：队友的 `multiturn-branch` 用固定的参考回复，模型的输出不回填，所以没测到"整段历史可复用"的情况。
- **短输入长输出**：队友的 `unique-decode` 只有 256 个输出、并发 1/8，没有测高并发下 decode 把 KV 撑满的情况。
- **Qwen3-4B（full attention）组**。
- **memory-timeline**：每个启动阶段占多少显存、服务时 KV 怎么被填满。

除注明外，环境同第一轮：
- RTX 5090 32 GB，SGLang v0.5.22（`baa9befa38`），没有改 runtime。
- 每个配置一台服务器；`--max-running-requests 64`，CUDA graph 和 overlap 开启，mem fraction 自动。
- drafter 用 cookbook 配置：EAGLE3 3/1/4、DFlash b16、DSpark block7。
- 单次运行。原始数据在 benchmark worktree 的 `work_dirs/stress-qwen3-8b/runs/gf-*`。

## 新负载

- **w-multiturn（多轮对话，回填输出）**：
  - 来源：1024 段真实 ShareGPT 对话，每段至少 4 个用户轮次（每轮 4–384 token），取前 4 轮。
  - 每个并发 worker 依次跑一段对话。下一轮的 prompt = 上一轮完整的 token 序列（prompt + 模型生成的回复 + `<|im_end|>`）+ 新的用户消息，所以包括模型输出在内的整段历史都是可复用的前缀。
  - 关闭思考（空 think 块），每轮最多 512 token，遇到 EOS 停。
  - 对话数 = max(8, 2 × 并发)。脚本是 `multiturn_bench.py`。
  - 这是 token 级的 append（agent 保留原始 token 的做法）。Qwen3 的 chat template 重新渲染历史时会去掉空 think 块，走 chat API 的复用会比这里少一点。
- **w4-longgen（短输入长输出）**：
  - 来源：2048 个 ShareGPT 首轮用户消息（16–256 token，英文、不含代码块）。
  - 用 Qwen3 默认的思考模式回答，`max_tokens` 2048，不忽略 EOS。
  - 实测平均输入 85 token，平均输出约 1,600–1,800 token。请求数 = max(8, 2 × 并发)。

## 1. Qwen3-8B：多轮对话

`gf-multiturn.csv`，单位 tok/s，括号里是相对 plain 的倍数。

| 并发 | plain | EAGLE3 | DFlash | DSpark |
|---:|---:|---:|---:|---:|
| 1 | 99 | 155（1.58） | 184（1.86） | 231（**2.34**） |
| 4 | 346 | 544（1.57） | 605（1.75） | 735（2.13） |
| 16 | 1153 | 1590（1.38） | 1393（1.21） | 2025（1.76） |
| 64 | **2259** | 1935（0.86） | 1306（**0.58**） | 2039（0.90） |

并发 64 的细节：

| | plain | EAGLE3 | DFlash | DSpark |
|---|---:|---:|---:|---:|
| KV 容量（token） | 58,687 | 43,609 | 38,542 | 38,093 |
| 前缀命中率 | **0.39** | 0.11 | 0.06 | 0.07 |
| 第 2 / 3 / 4 轮命中率 | 0.85 / 0.51 / 0.17 | 0.44 / 0.03 / 0.06 | 0.20 / 0.02 / 0.03 | 0.25 / 0.02 / 0.04 |
| 平均同时运行 / 排队 | 40.6 / 13.1 | 34.2 / 19.4 | 32.9 / 21.6 | 30.9 / 22.3 |
| TTFT 中位数 | **0.37 s** | 3.9 s | 7.6 s | 4.9 s |

- **并发 16 及以下，每种配置都能复用整段历史**：第 2–4 轮命中率 0.91–0.98，推测解码快 1.2–2.3 倍。
- **并发 64 时历史保不住，推测解码保得更少**：
  - 64 段对话的历史加起来超过了 KV 容量。两轮之间，一段对话的历史就被别的请求挤出去了，下一轮只能整段重算。
  - plain 到第 4 轮命中率也只剩 0.17，推测配置从第 3 轮起就接近 0。
  - 重算加重了 prefill，排队变长：推测配置的 TTFT 中位数是 plain 的 10–20 倍。
- 和 W2 共享前缀（并发 64：0.50–0.72 倍）相比，这里 DSpark（0.90）和 EAGLE3（0.86）输得少。这个负载 decode 更多（每轮约 440 个输出 token），推测在计算上的优势抵掉了一部分容量损失。
- 72–84% 的回复写满了 512 token 的上限。

## 2. Qwen3-8B：短输入长输出

`gf-longgen.csv`，单位 tok/s。

| 并发 | plain | EAGLE3 | DFlash | DSpark |
|---:|---:|---:|---:|---:|
| 1 | 99 | 160（1.62） | 162（1.63） | 177（1.79） |
| 4 | 293 | 528（1.80） | 554（1.89） | 616（2.10） |
| 16 | 923 | 1518（1.65） | 1167（1.26） | 1926（**2.09**） |
| 64 | **2286** | 2199（0.96） | 1287（**0.56**） | 2215（0.97） |

并发 64 的细节：

| | plain | EAGLE3 | DFlash | DSpark |
|---|---:|---:|---:|---:|
| 平均同时运行 / 排队 | **39.2** / 11.2 | 31.9 / 19.8 | 32.3 / 21.0 | 28.2 / 23.3 |
| TPOT 中位数 | 17.1 ms | 15.3 ms | **27.3 ms** | **13.1 ms** |
| TTFT 中位数 | 8.6 s | 13.4 s | 28.3 s | 18.9 s |
| 被 retract 的请求 | 23 | 17 | 6 | 9 |

- 这个场景里推测解码的收益保持得最久：并发 16 时 DSpark 仍快 2.09 倍，EAGLE3 快 1.65 倍。
- **并发 64 时，EAGLE3 和 DSpark 输在能同时跑的请求数，不在计算**：
  - 它们每个请求的 decode 仍比 plain 快（TPOT 13–15 ms 对 17 ms）。
  - 但 KV 少了 26–35%，每个请求最后要占约 1.8K token，同时运行的请求只有 28–32 个（plain 39 个），所以总吞吐只追平 plain（0.96–0.97）。
- **DFlash 两个问题叠加**：容量一样受限，再加上宽度 16 的 verify 让每步变慢（TPOT 27 ms），所以只有 0.56 倍。这和第一轮 w1-natural 并发 64 的 0.50 倍一致。
- 长输出把 KV 撑满靠的是 decode，不是前缀，所以 HiCache 这类前缀卸载在这里帮不上，只能靠显存划分。

## 3. memory-timeline

启动部分来自 server log：每个阶段之后的 `avail mem`，相对加载权重前的空闲显存。服务部分来自 1 秒一次的 `/metrics` 和 NVML 采样。

`memory-timeline-8b-w2c64-startup.csv`（Qwen3-8B，单位 GB，括号里是该阶段增加的量）：

| 阶段 | plain | EAGLE3 | DFlash | DSpark |
|---|---:|---:|---:|---:|
| target 权重 | 15.28 | 15.28 | 15.28 | 15.28 |
| draft 权重 | — | 17.51（+2.23） | 17.23（+1.95） | 17.38（+2.10） |
| target KV 池 | 23.76（+8.48） | 23.55（+6.04） | 22.97（+5.74） | 23.04（+5.66） |
| draft KV 池 | — | 23.72（+0.17） | 23.72（+0.75） | 23.79（+0.75） |
| CUDA graph（全部） | 25.26（+1.50） | 25.86（+2.14） | 27.25（+3.53） | 26.64（+2.85） |

- KV 池之前的总量都是约 23.7 GB（由 static fraction 决定）。draft 权重和 draft KV 全部从 target KV 里扣。
- graph 是在池子之后捕获的，推测配置多出来的 0.6–2.0 GB graph 落在 static 预算之外。
- 服务时间线：
  - `memory-timeline-8b-w2c64-serving.csv` 和 `memory-timeline-8b-multiturn-c64-serving.csv` 逐秒记录 KV 已用 token、同时运行和排队的请求数。
  - 所有配置（包括 plain）的 KV 池都会用到 90% 以上，并一直停在高位：W2 3–4 秒到，多轮对话 11–37 秒到。差别在于同样满的池子能撑住几个请求：
    - W2 并发 64 时平均同时运行：plain 25.4，EAGLE3 16.8，DFlash 13.6，DSpark 12.8。
    - 多轮对话：plain 40.6，推测配置 31–34。
- `memory-timeline-27b-startup.csv`（27B hybrid，用 E2 调参后的配置）：
  - 推测配置的 state + KV 池只有 1.9–3.7 GB，plain 是 7.2 GB。
  - MTP 那一行在捕获 graph 时已用显存**下降了 3.9 GB**：MTP 头自带的 embedding / lm_head 在池子分完之后才释放，也就是第一轮问题七的记账缺陷，在时间线上直接看得到。

## 口径与限制

- 单次运行。第一轮的复现显示，并发 ≥ 8 的单格可能有最多 34% 的偏差。
- 多轮负载每轮输出上限 512，大部分回复被截断；对话数随并发增加，并发 64 时 128 段对话。
- 长输出负载是思考模式的推理文本，接受长度（EAGLE3 2.4、DFlash 2.6、DSpark 3.2）和自然对话相近。
- `retracted_reqs` 来自 server log 里每个点时间窗口内的 `Retract requests` 行。平均同时运行和排队取有请求在跑的采样点。
