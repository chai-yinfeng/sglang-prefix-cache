# Policy 第四轮：找 policy 真正起作用的场景（2026-10-28）

第三轮的结论是：在 Qwen3-8B + DSpark 上，policy 层基本不起作用。DSpark 自带的置信度规划器已经按负载调 verify 宽度，policy 的三个执行器只在特定条件下才动。这一轮把可能让 policy 起作用的实验都试一遍：

| 编号 | 实验 | 结论 |
|---|---|---|
| w1 | DFlash（没有规划器）静态 verify 宽度扫描，自然对话和校对两种负载 | 最优宽度同时随负载和负载类型变，任何一个静态宽度都有严重吃亏的场景 |
| w3 | 运行时改 DFlash verify 宽度：正确性、eager 开销 | 输出逐 token 是 target 的 argmax；c64 时 eager 不比 graph 慢，c16 慢约 12% |
| w4 | 时变负载下的宽度 policy（`--speculative-policy width`）对比静态配置 | 见下文 |
| w2 | Qwen3.5-4B hybrid：DFlash 宽度同时决定 verify 中间状态的显存 | 见下文 |
| 不做 | DSpark 上找低接受率的真实负载 | ShareGPT 里只有 27 条中日韩对话，凑不够并发 64；temperature 1.0 时 DSpark 接受长度仍有 2.36（第三轮），暂停不会赢 |

- 环境：Qwen3-8B BF16，RTX 5090，flashinfer（DFlash 默认），CUDA graph 和 overlap 开启，capture 后定池大小（`SGLANG_ENABLE_POST_CAPTURE_KV_SIZING=1`），page 1；DFlash 是 `z-lab/Qwen3-8B-DFlash-b16`。单次运行。
- 原始数据：`work_dirs/stress-qwen3-8b/runs/r4-*`。

## w1：DFlash 的最优 verify 宽度随负载和负载类型变

DFlash 每步 draft 一个固定 16 个位置的块，target 全部 verify。`--speculative-dflash-block-size k` 可以在启动时改块大小（draft 和 verify 都只做前 k 个位置）。两种负载：

- **w1-natural**：ShareGPT 真实对话，自然结束（第三轮的负载）；
- **w-edit**：校对任务（新增，`make_edit_workload.py`）。prompt 是"改正下面这段文字的拼写和语法，原样输出全文"，文字取自 ShareGPT 里 150–500 token 的英文回复，带 `/no_think`。输出基本是在抄输入，所以接受率很高。

吞吐（tok/s）/ 接受长度，`w1-static-width.csv`：

| 负载 | 配置 | c1 | c4 | c16 | c64 |
|---|---|---|---|---|---|
| 自然对话 | b16 | **150** / 2.22 | **489** / 2.20 | 880 / 2.21 | 1067 / 2.23 |
| | b8 | 145 / 2.12 | 475 / 2.09 | 1131 / 2.08 | 1575 / 2.12 |
| | b4 | 134 / 1.92 | 457 / 1.92 | **1179** / 1.94 | 2043 / 1.96 |
| | b3 | 132 / 1.82 | 432 / 1.82 | 1093 / 1.81 | **2151** / 1.82 |
| | b2 | 112 / 1.54 | 378 / 1.54 | 952 / 1.54 | 2095 / 1.55 |
| | plain | 98 | 328 | 836 | 2116 |
| 校对 | b16 | **742** / 11.67 | **2267** / 11.72 | **3767** / 11.48 | 4446 / 11.71 |
| | b8 | 463 / 6.98 | 1504 / 6.94 | 3647 / 7.00 | **4658** / 7.03 |
| | b4 | 264 / 3.81 | 926 / 3.80 | 2594 / 3.80 | 4360 / 3.80 |
| | b2 | 144 / 1.96 | 510 / 1.96 | 1550 / 1.95 | 3553 / 1.95 |
| | plain | 99 | 346 | 1108 | 2909 |

- **自然对话**：低负载时 b16 最好（plain 的 1.5 倍）；高负载时 b16 只有 plain 的 0.50 倍，b3 最好（1.02 倍）。原因和第一阶段 Q5 一样：并发 64 时一步要 verify 1024 个 token，已经是计算瓶颈，而每个请求平均只接受 2.2 个。
- **校对**：b16 在 c1–c16 都最好（c1 是 plain 的 7.5 倍），c64 时 b8 略好（+5%）。接受长度 11.7，宽窗口几乎不浪费。
- **任何一个静态宽度都有严重吃亏的场景**：b16 在自然对话 c64 只有最优的 50%；b3/b4 在校对 c1 只有 b16 的 36%。最优宽度同时取决于负载和接受率，而这两样在线上都会变。这正是运行时 policy 能比任何静态配置都好的地方。
- 块变窄后的接受长度（2.22 → 1.92 → 1.54）和"截断的几何分布"基本吻合，说明 DFlash 的 draft 块截短后，前几个位置的预测质量几乎不变。

## w3：运行时改 DFlash 的 verify 宽度

### 实现（`lvelf/policy-layer`）

| 位置 | 改动 |
|---|---|
| `speculative/dflash_worker_v2.py` | decode 步骤按运行时宽度 `w`（1..block）只 draft 和 verify 前 `w` 个位置：草稿缓冲区按 `w` 重新取行（`_rows`），draft 前向拆成 `_propose_block_drafts`；`w=1` 时不跑 draft，只 verify bonus token，target hidden 照常注入 draft KV，所以恢复宽窗口时上下文完整。宽度小于 block 时用不上已 capture 的 graph，走 eager |
| `set_dflash_verify_width` / `/set_internal_state {"dflash_verify_width": w}` | 运行时开关；只支持贪心 draft head，不支持 compact draft cache 和 Mamba verify 状态（`supports_verify_width`） |
| `spec_policy/` | plan 新增 `verify_width`，执行器调用上面的开关；`--speculative-policy width` 见 w4 |

### 正确性

同一个 b16 服务，6 个 prompt 贪心生成 160 个 token，分别在宽度 16（参考）、4、2、1、生成途中切换宽度（16 → 1 → 3 → 16），以及再跑一次 16。然后用一个 plain 服务对每个输出做 teacher-forced 打分，看每个 token 是不是 target 的 top-1（`w3-teacher-forced.csv`）：

- 所有变体中，不是 top-1 的 token 与 top-1 的差距都 ≤ 0.25 nat，和宽度 16 的参考、以及同宽度重跑的量级一样，属于 bf16 的近似平局。
- 逐字比较时各宽度在 75–800 个字符处开始不同，但宽度 16 自己重跑也会在 387、793 处不同（批次组成不同导致近似平局翻转）。
- 结论：窄宽度路径输出的每个 token 都是 target 的 argmax。

### eager 开销

同一个 b16 服务在运行时切到宽度 k，对比启动时就设成 bk 的服务（有 graph），w1-natural，`w3-runtime-width.csv`：

| 并发 | 宽度 | 运行时（eager） | 静态 bk（graph） | 接受长度（运行时 / 静态） |
|---|---|---|---|---|
| 16 | 4 | 1039 | 1179 | 1.94 / 1.94 |
| 16 | 3 | 997 | 1093 | 1.81 / 1.81 |
| 64 | 4 | 2088 | 2043 | 1.95 / 1.96 |
| 64 | 3 | **2240** | 2151 | 1.82 / 1.82 |
| 64 | 2 | 2153 | 2095 | 1.55 / 1.55 |
| 64 | 1 | 1869 | - | 1.0 |

- c64 时 eager 不比 graph 慢（一步 verify 192 个 token 要 20 ms，CPU 发射 kernel 的时间被盖住）；c16 时慢 9–12%。
- 接受长度和静态块完全一致。
- 宽度 1（只 verify bonus）在 c64 是 1869，低于 plain 的 2116：draft KV 照常注入、verify 走 eager，都有开销。所以对 DFlash 来说，"关推测"不如"窄窗口"。

## w4：时变负载下的宽度 policy

### 策略（`--speculative-policy width`，`SpecWidthPolicy`）

按实测 decode 吞吐在宽度阶梯 16 / 8 / 6 / 4 / 3 / 2 / 1 上爬山，测量方式沿用第三轮的 regime 策略（64 步一个窗口，切换后丢掉 4 步，margin 3%，过期或负载变化 25% 才重新测量，连续失败就把间隔翻倍）：

- 新一轮开始时，先在当前宽度测一个窗口作为基准（触发这一轮的窗口可能跨了负载变化，不能当基准），然后往一个方向走一格；更好就继续走，第一步就变差就换方向试一次，否则停下。负载上升先往窄走，下降先往宽走。
- 只统计实际以当前宽度运行的步（overlap 调度器会晚一步生效）。
- 两个按 verify token 数定的界（实测，见 `policy.py` 的注释）：
  - **下界 64**：一步不到 64 个 verify token 时，步时和更宽的窗口几乎一样（c1–c16 从 8 到 64 个 token 步时差 10% 以内），所以更窄只会少接受，从不尝试。每个窗口都检查：负载一降到下界以下，立即回到下界对应的宽度，正在进行的一轮也放弃。并发 4 时这把宽度固定在 16。
  - **上界 256**：超过后一步是计算瓶颈。如果上一个窗口只用上了不到 1/4 的 verify 位置，负载跳变时在**第一步**就直接跳到上界以内最宽的一格，再从那里爬山。接受率高的负载（校对，16 个位置用上 11.7 个）不跳，可以停在宽窗口。

开发过程中按实测结果改了四次，每次单独提交：

| 版本 | 改动 | 起因 |
|---|---|---|
| v1 | 只有爬山 | — |
| v2 | 加上下界 | v1 在并发 4 时被噪声带到窄宽度（4 个请求的窗口，接受率波动超过 3% margin）；负载跳到 64 后要一格一格从 16 往下爬 |
| v3 | 上界只在"窗口大部分浪费"时才跳 | 校对负载在 c64 时宽窗口仍然划算，上界不能一刀切 |
| v4 | 每个窗口检查下界 | 校对负载 c64 → c4 时，爬山还在进行中，结束在宽度 6，之后 1024 步不重测，比整个阶段还长 |
| final | 负载跳变的第一步就跳 | 每个 c64 阶段开头要先以宽度 16 跑满一个窗口（带 prefill 时约 100 ms 一步），约 7 秒 |

### 实验

`phase_bench.py`：同一个服务按顺序跑几个闭环阶段，每个阶段 `并发:请求数`，阶段之间请求不重复；所有配置跑同一串请求，比较总时间。三组：

- **自然对话**：c4 × 64 → c64 × 512 → c4 × 64 → c64 × 512；
- **校对**：同样的阶段；
- **混合**：负载类型和并发都变：自然对话 c64 × 384 → 校对 c4 × 48 → 校对 c64 × 384 → 自然对话 c16 × 128 → 自然对话 c4 × 48 → 校对 c16 × 128。

### 结果

总时间（秒，越小越好），`w4-phases.csv`：

| 负载 | width policy（最终版） | 最好的静态宽度 | b16 | plain | 各阶段事后最优的组合 |
|---|---|---|---|---|---|
| 自然对话 c4 ↔ c64 | **162.8** | 171.4（b3） | 299.1 | 203.2 | 约 161 |
| 校对 c4 ↔ c64 | 85.4 | **84.9**（b16） | 84.9 | 214.7 | 约 85 |
| 混合 | **131.8** | 149.8（b4） | 197.1 | 227.9 | 约 130 |

- 三组里 policy 都不比最好的静态配置差：自然对话快 5%，校对持平，混合快 12%。混合负载里它离"每个阶段事后挑最优配置"只差约 1%。
- 静态配置只能对一种负载调好：b3/b4 在自然对话高负载最好，但在校对低负载只有 b16 的 40%；b16 正好相反。混合负载里任何一个静态宽度都要吃其中一边的亏，这是 policy 赢得最多的地方。
- 相对 plain：自然对话快 20%，校对快 60%，混合快 42%。

混合负载各阶段（tok/s）：

| 阶段 | policy | b16 | b8 | b4 | plain | policy 的宽度轨迹 |
|---|---|---|---|---|---|---|
| 自然对话 c64 | **3191** | 1224 | 1933 | 2729 | 2898 | 第一步从 16 跳到 4，再爬到 3 |
| 校对 c4 | **2211** | **2211** | 1504 | 910 | 340 | 下界把宽度拉回 16 |
| 校对 c64 | 4533 | 4530 | **4706** | 4444 | 2986 | 停在 16（阶段太短，只有约 2 个窗口，没来得及试 8） |
| 自然对话 c16 | 1339 | 1073 | 1526 | **1587** | 1124 | 16 → 8 → 6（变差）→ 8；窄宽度走 eager，比静态 b8 慢 |
| 自然对话 c4 | **519** | 514 | 509 | 476 | 322 | 16 |
| 校对 c16 | **3759** | 3766 | 3631 | 2576 | 1106 | 16 |

|---|---|---|---|---|

### 局限

- 都是单次运行。同一配置同一阶段重复时差 2–3%（例如 b16 校对 c4 两个阶段 2308 / 2246）。policy 的优势在混合负载上（12%）明显大于噪声，在自然对话上（5%）接近噪声的两倍。
- 中等负载（c16）窄宽度走 eager，比同宽度的静态 graph 慢 9–15%。给每个窄宽度单独 capture target verify graph 可以补回来（EAGLE 的 adaptive 有现成做法：每档一个 attention backend + graph runner），但要处理和 breakable prefill graph 共用 attention backend 的问题，没有做。
- 宽度对一个 batch 里的所有请求一样。接受率差别大的请求混在一起时，按请求分配宽度（DSpark 规划器那样的 ragged verify）会更好；DFlash 要先移植 ragged verify。
- 两个 verify token 界（64 / 256）是在 Qwen3-8B / RTX 5090 / flashinfer 上测的，换模型或 GPU 要重测。
- 窗口很短的阶段里 policy 来不及试探（校对 c64 只有约 2 个窗口），会停在进入时的宽度。

## w2：Qwen3.5-4B hybrid 上，verify 宽度同时决定显存划分

模型 `Qwen/Qwen3.5-4B`（24 层 GDN + 8 层 full attention），drafter 是 `z-lab/Qwen3.5-4B-DFlash`（block 16）。默认配置（`extra_buffer`，overlap 开，fp32 SSM 状态，`--mamba-full-memory-ratio` 默认），w1-natural，`w2-hybrid-width.csv`：

| 配置 | 请求上限 | c1 | c4 | c16 | c64 |
|---|---|---|---|---|---|
| DFlash b16 | **4** | **302** / 3.99 | 927 / 3.89 | 969 | 1000 |
| DFlash b8 | 8 | 294 / 3.55 | **967** / 3.54 | 1449 | 1643 |
| DFlash b4 | 12 | 266 / 2.84 | 813 / 2.85 | **1640** | **1918** |
| DFlash b2 | 16 | 178 / 1.83 | 558 / 1.83 | 1242 | 1629 |
| MTP（3/1/4） | 12 | 237 / 2.88 | 746 / 2.89 | 1482 | 1741 |
| plain | 26 | 160 | 527 | 1162 | 1916 |

- **请求上限是 Mamba 状态池给的**：每个运行中的请求占 5 个状态槽（`extra_buffer` + overlap），推测时再加上 D 个 verify 中间状态（每个 48.4 MB，fp32），所以 b16 每个请求约 1 GB。默认的状态池 / KV 划分不考虑 D，b16 只能跑 4 个请求，而 KV 池有 13 万个 token（4 个请求只用得上几千），启动后还空着 8 GB。
- 结果是最优宽度随负载变化，原因和 8B 不同：8B 上是计算（窄窗口少 verify），这里主要是显存（窄窗口每个请求占的状态少，能并发更多请求）。c1 是 b16，c4 是 b8，c16/c64 是 b4。
- c64 时最好的 DFlash（b4，1918）也只和 plain（1916）持平，c16 时 b4 是 plain 的 1.41 倍。

### 按 verify 宽度划分状态池和 KV 池

每个配置按"每个请求 (5 + D) 个状态槽 × 48.4 MB + 约 2K token 的 KV"在同样的池预算（DFlash 约 11.9 GB，plain 约 13.4 GB）里算出请求上限 N，用 `--max-mamba-cache-size 5N --max-running-requests N` 固定下来（`w2-hybrid-split.csv`）：

| 配置 | 请求上限（默认 → 重新划分） | KV token | c16 | c64 |
|---|---|---|---|---|
| DFlash b16 | 4 → 9 | 130K → 38K | 969 → **1278**（+32%） | 1000 → **1421**（+42%） |
| DFlash b8 | 8 → 15 | → 40K | 1449 → 1723（+19%） | 1643 → 2160（+31%） |
| DFlash b4 | 12 → 20 | → 57K | 1640 → **1758**（+7%） | 1918 → 2345（+22%） |
| DFlash b2 | 16 → 24 | → 70K | 1242 → 1315（+6%） | 1629 → 2081（+28%） |
| MTP | 12 → 24 | → 46K | 1482 → 1622（+9%） | 1741 → 2330（+34%） |
| plain | 26 → 40 | 232K → 124K | 1162 → 1169（+1%） | 1916 → **2471**（+29%） |

- 默认划分对这个负载（短上下文）整体偏向 KV，所以 plain 在 c64 也涨了 29%。但 verify 越宽涨得越多（b16 +42%），因为默认公式没有算每个请求的 D 个中间状态。
- 重新划分后：c16 时 DFlash b4 是 plain 的 1.50 倍、MTP 的 1.08 倍；c64 时 plain（2471）仍然最好，b4 差 5%。
- 这是设计里的执行器 ①（显存划分）第一次在本项目里有明显收益。这里是启动时手算的；能不能变成一条规则，见下一节。运行中随宽度改划分（窄窗口释放的中间状态换成更多请求槽）需要运行时调整 Mamba 池，这一轮没有做。

### 一条不依赖负载的规则

配置器其实已经把 verify 中间状态算进了状态池预算（`kv_cache_configurator.py` 里 main state 和 intermediate 的联合求解），但状态池占总预算的比例固定是 0.9 / 1.9，和 D 无关，所以 D 越大能跑的请求越少。把默认比例按 (S + D) / S 放大（S = 每个请求的状态槽数，这里是 5），不需要知道负载（`h-dflash-*-rule`，同一个 csv）：

| 配置 | 默认 | 规则（比例 0.9 × (S+D)/S） | 手算划分 |
|---|---|---|---|
| b16 c16 / c64 | 969 / 1000（上限 4） | 1267 / 1368（上限 8） | 1278 / 1421（上限 9） |
| b4 c16 / c64 | 1640 / 1918（上限 12） | 1773 / 2248（上限 16） | 1758 / 2345（上限 20） |

这条规则拿到了手算划分 75–90% 的收益。它可以作为 hybrid + 推测的默认比例（用户没有显式设置 `--mamba-full-memory-ratio` 时），但这会改变所有 hybrid 推测部署的显存划分，需要在更多模型上验证，这一轮没有改默认值。

## 结论：policy 现在什么时候有用

- **有用**：被推测的算法自己没有按负载调节的机制时。DFlash 的 verify 宽度是固定的，而最优宽度同时随负载和负载类型变：
  - 运行时宽度 policy 在三组时变负载上都不比最好的静态配置差（自然对话快 5%，校对持平，混合快 12%），比 plain 快 20–60%。
  - 混合负载上离"每个阶段事后挑最优"只差约 1%。
- **有用（显存一侧）**：hybrid 模型上，verify 宽度决定每个请求占多少状态。按宽度划分状态池和 KV 池，DFlash b16 在 c64 快 42%，b4 快 22%。一条 (S + D) / S 的比例规则就能拿到大部分收益。
- **没有用**：DSpark（第三轮）。它的置信度规划器已经按负载调宽度，policy 只在优先级、扩池余量、接受率崩溃这些条件下才动。
- **还没做**：
  - 窄宽度的 verify graph（补回中等负载 9–15% 的 eager 开销）；
  - 按请求分配宽度（DFlash 先要有 ragged verify）；
  - 运行中随宽度调整 Mamba 池；
  - 把 (S + D) / S 规则做成默认值。
