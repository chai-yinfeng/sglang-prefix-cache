# A 组结果：Qwen3-8B（E1、E2，2026-10-27）

原始数据和完整表格在 worktree 的 `work_dirs/stress-qwen3-8b/runs/e2-v1/`（`RESULTS.md`、`summary.csv`）。harness 是 `run_stress.py`，分析脚本是 `analyze.py` / `report.py`。

**配置**：v0.5.22 `baa9befa38`，RTX 5090。cookbook 默认参数：CUDA graph 和 overlap 开启，`mem_fraction_static` 自动（解析为 0.776）。另外设置 `--max-running-requests 64 --cuda-graph-max-bs-decode 64`。EAGLE3 用 cookbook 的 3/1/4；DFlash 和 DSpark 用 checkpoint 自带的 block 大小。所有点都是**单次运行**，并发 ≥ 8 的点有一定波动（复现实验里单格最大偏差 34%）。

**负载**：
- W1 decode-heavy：`random` 数据集（取 ShareGPT 的 token），输入 1024，输出 512，`ignore_eos`；
- W2 共享前缀：24 组真实文档前缀，每组 4096 token，组间按 Zipf(α=1) 分布，问题约 20 token，输出 128。前缀工作集约 98K token。

## E1 显存构成

| 算法 | target 权重 | draft 权重 | target KV | draft KV | CUDA graph | 初始化后剩余 | target KV 容量 (token) |
|---|---:|---:|---:|---:|---:|---:|---:|
| plain | 15.28 | 0 | 8.06 | 0 | 0.92 | 4.84 | 58,687 |
| EAGLE3 | 15.28 | 2.23 | 5.98 | 0.16 | 2.64 | 4.24 | 43,609（-26%） |
| DFlash | 15.28 | 1.95 | 5.30 | 0.74 | 2.91 | **0.47** | 38,542（-34%） |
| DSpark | 15.28 | 2.10 | 5.24 | 0.72 | 2.23 | 3.46 | 38,093（-35%） |

单位 GB。

- static 预算（权重 + KV 池）在四种配置下都约为 23.3 GB。**draft 的权重和 KV 全部从 target KV 里扣**。
- **target KV 少掉的部分，大头是 draft 权重（1.95–2.23 GB），draft KV 只占 0.16–0.74 GB。** 即使把 draft KV 全部丢掉，也只能收回 DSpark 损失的约 1/4（0.72 / 2.82 GB）。这进一步说明，"draft KV 保留策略"针对的只是较小的那一块。
- 推测解码的 CUDA graph 占 2.2–2.9 GB（plain 只有 0.92 GB），这部分不在 static 预算内。DFlash 初始化后只剩 0.47 GB，余量很小。

- 收益随并发增大单调下降，但始终 > 1。
- 并发 64 时所有配置都受 KV 容量限制：最大 running 请求数 plain 为 38，推测解码只有 24–28，排队 43–54 个；TTFT p50 达到 7–11 秒。
- **注意**：W1 的接受长度偏高（DFlash 6.3–7.4，DSpark 5.8–6.3），因为 `ignore_eos` 让模型在本该结束之后继续生成重复文本。所以 W1 低并发时的加速比被高估了，需要用自然结束的输出复核（见后续）。

- **在显存压力加前缀复用的负载下，推测解码从并发 16 起比 plain 还慢**；到并发 64 时只有 plain 的 50–72%。

- 高并发时推测解码的 TPOT 也比 plain 差（DFlash 22–26 ms，plain 17–19 ms）。可能是 prefill 重算打断了 decode，也可能是大 batch 下 verify 本身的开销，待 E5 profiling 区分。
- 接受长度比较真实（EAGLE3 约 2.4，DFlash 约 2.3，DSpark 约 3.0），不随并发变化。

- **容量相同时，推测解码的命中率和 plain 几乎一样**（并发 64：EAGLE3 0.71 vs 0.69；DSpark 0.62 vs 0.64）。命中率下降完全是 KV 容量造成的。
- **容量相同时，推测解码仍然是正收益**：EAGLE3 比 plain-kv43609 快 1.11–1.17 倍，DSpark 比 plain-kv38093 快 1.12–1.18 倍（并发 16–64）。DFlash 例外，并发 ≥ 16 时只有 0.93–0.96 倍，它的 TPOT 明显偏高（22–26 ms）。

- 工作集约 98K token，接近容量的区间里，吞吐对容量非常敏感：容量少 35%，吞吐少 46%。

### W1 decode-heavy
- 并发 ≤ 16 时，容量不影响结果（三种 plain 完全一样）。
- 并发 32 和 64 时，plain-kv38093 比满容量的 plain 慢 22–23%（1301/1372 vs 1671/1793 tok/s），最大 running 请求从 32–38 个降到 24 个。
- DSpark 相对同容量 plain 仍有约 2 倍加速（2775 vs 1372，并发 64）。

## W1 复核：自然对话（w1-natural）

ShareGPT 的真实对话套 chat template，不忽略 EOS；最大输出长度取参考回复的长度。Qwen3 在思考模式下所有请求都生成到长度上限，所以输出是正常的推理文本，没有 EOS 之后的重复。平均每个请求输入约 430 token，输出约 240 token。

| 并发 | EAGLE3 | DFlash | DSpark | plain tok/s |
|---:|---:|---:|---:|---:|
| 1 | 1.65× | 1.54× | 1.90× | 98 |
| 4 | 1.65× | 1.51× | 1.88× | 328 |
| 16 | 1.58× | **1.05×** | 1.73× | 838 |
| 64 | 1.03× | **0.50×** | 0.92× | 2118 |

- 接受长度回到正常水平：EAGLE3 约 2.3，DFlash 约 2.2，DSpark 约 2.8。原 W1（ignore_eos）中 DFlash/DSpark 的 5.8–7.4 和 3.8–4.1 倍加速**是被高估的**，以本节数字为准。
- 即使是 decode-heavy 负载，到并发 64，推测解码也不比 plain 快。**这里主要是计算问题**：DFlash 每个请求每步都 verify 16 个 token 的 block，batch 64 时 TPOT 达到 53 ms（plain 21 ms），而平均只接受 2.2 个 token。
- 因此高负载下推测解码变慢有两个独立原因：**显存**（W2，KV 容量被挤占）和**计算**（大 batch 下 verify 开销不划算）。

## E4：自带的自适应推测（`--speculative-adaptive`，EAGLE3）

默认配置下，**自适应 EAGLE3 在所有并发档都比固定 EAGLE3 差，大多数点甚至比 plain 还差**：

| 负载 / 并发 | plain | EAGLE3 | EAGLE3 adaptive |
|---|---:|---:|---:|
| W2 并发 1 | 88 | 135 | 78 |
| W2 并发 16 | 654 | 620 | 251（TPOT 51 ms） |
| W2 并发 64 | 984 | 710 | 293 |
| w1-natural 并发 16 | 838 | 1323 | 393 |
| w1-natural 并发 64 | 2118 | 2178 | 768（接受长度 1.38） |

原因（来自 server log）：adaptive 为每个候选推测步数（默认配置的并集是 0/1/3/5/7）各建一套运行状态和 CUDA graph，**每套 1.2–1.6 GB**。启动后可用显存降到 **0.00 GB**，之后都在显存耗尽的状态下运行。另外 batch 1 时它在 3 步和 5 步之间来回切换。

结论：**自带的自适应推测是在拿显存换计算上的灵活性**，在 32GB 卡上不调参就会让显存问题更严重。这说明计算和显存两个问题是耦合的，不能分开解决。

### 精简配置（`eagle3-adaptive-lite`，候选步数只保留 {0, 1, 3}，`inputs/adaptive-lite.json`）

只多建了两套运行状态（约 2.4 GB），启动后还剩约 2.7 GB 空闲，没有再出现显存耗尽。

| 负载 / 并发 | plain | 同容量 plain | EAGLE3 固定 | adaptive 默认 | adaptive 精简 |
|---|---:|---:|---:|---:|---:|
| W2 并发 16 | 654 | 534 | 620 | 251 | 619 |
| W2 并发 64 | **984** | 642 | 710 | 293 | 706 |
| w1-natural 并发 16 | 838 | - | 1323 | 393 | 1329 |
| w1-natural 并发 64 | 2118 | - | 2178 | 768 | 2155（接受长度 1.39） |

- 精简版的表现和固定 EAGLE3 一致。并发 64 时接受长度降到 1.39，说明大部分步不再推测，吞吐和 plain 持平，但没有超过。
- **它补不回显存损失**：W2 并发 64 时仍比满容量 plain 少 28%（706 vs 984），因为 draft 的权重、KV 和 graph 照样占着，KV 容量还是 43.6K。
- **结论：计算这一侧，现有自适应机制能处理（前提是调小候选集合）；显存这一侧，现有系统没有任何机制能处理。** 后者是第二阶段最可能做出贡献的方向。

## 重复性（`e2-rep2`）

plain/EAGLE3/DFlash/DSpark 在 W2 和 w1-natural 上又完整跑了一轮（并发 1/4/16/32/64）。与第一轮共有 36 个点可以对比，吞吐比值中位数 **1.000**，范围 0.993–1.060；W2 的前缀命中率与第一轮记录的数字一致。结论可以视为稳定。

补充的 w1-natural 并发 32 数据：plain 1274，EAGLE3 1820（1.43 倍），DFlash 976（0.77 倍），DSpark 1701（1.33 倍）。并发 64 时各算法实际同时运行 60–64 个请求（请求短，KV 装得下），所以那里推测解码不划算**纯粹是计算原因**；W2 则是显存原因。

## 初步结论

1. **在 W2 这类负载下，最大的提升空间来自显存，而不是 draft 本身。** 推测解码把 target KV 容量压缩了 1/4 到 1/3，在有前缀复用、接近容量边界的负载中，命中率和并发都会下降，最终比 plain 更慢。E3 对照已经证实这一点：容量相同时，推测解码仍比 plain 快 11–18%（DFlash 除外），慢下来的部分全部来自容量损失。
2. **draft 权重是 KV 损失的主因，draft KV 是次要的。** 只管理 draft KV 的保留策略，最多只能收回约 1/4 的损失。
3. **显存是静态划分的**：即使在高负载下推测解码已经不划算，它占用的 draft 权重、draft KV 和 graph 显存也不会让给 target。

候选方向（待验证）：按负载动态开关推测解码，并把 draft 的显存池还给 target KV；在不划算时卸载 draft 权重；缩减推测解码的 graph 显存。
