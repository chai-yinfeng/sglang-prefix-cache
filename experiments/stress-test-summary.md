# 提升空间地图（第一阶段 P5，2026-10-27）

> 2026-10-27 更新：后续调查见 `phase1-followups-v0.5.22/FINDINGS.md`。其中修正了两点：现有系统并非完全没有显存管理（有分组件的池子、HiCache、hybrid 统一字节池），只是不会随负载把 draft 权重、graph、verify 空间还给 target；MTP 那 5 GB 闲置已用诊断补丁证实。

依据：`02-results-A-qwen3-8b.md`（Qwen3-8B dense，BF16）和 `03-results-B-qwen38-27b.md`（Qwen3.8-27B NVFP4 hybrid），单卡 RTX 5090 32GB，SGLang v0.5.22。A 组主要结果做过两轮，比值中位数 1.000；B 组为单次运行。

## 一句话

**在显存受限的单卡上，推测解码在低负载时加速 1.5–2 倍；负载一高，它就因为占用显存而比不开还慢（plain 的 0.26–0.72 倍）。现有系统对计算开销有自适应机制，对显存占用完全没有。** 原 proposal 关注的 draft KV 只是显存占用里很小的一块。

## 两种损失机制

| | 现象 | 证据 | 现有机制 |
|---|---|---|---|
| **显存挤占** | draft 的权重、KV、verify 中间状态是静态划分的，直接压缩 target 的 KV 和 state 池，导致并发变少、前缀命中率下降 | A：KV 容量少 26–35%，W2 并发 64 时只有 plain 的 0.50–0.72 倍；**同容量的 plain 也掉到同样水平**（E3），推测解码本身仍有 +11–18%。B：并发上限从 15 降到 2–4，W2 并发 16 时只有 0.26–0.44 倍，命中率 0.6–0.7 降到 0.16–0.32 | **没有** |
| **计算浪费** | 大 batch 下 verify 的 token 大部分被拒绝 | A：w1-natural 并发 64 时所有请求都装得下，推测解码仍只有 0.50–1.04 倍；DFlash（block 16）TPOT 53 ms，plain 21 ms | `--speculative-adaptive`，只支持 EAGLE；默认配置为每个候选步数建一套 graph，在 32GB 卡上把显存耗尽（性能降到 0.3–0.45 倍）；调小候选集合后能与 plain 持平，但补不回显存损失 |

## 显存都去哪了（每多支持一个请求要付出的代价，以及固定开销）

| 项目 | A：Qwen3-8B | B：Qwen3.8-27B | 是不是原 proposal 的目标 |
|---|---|---|---|
| draft 权重（固定） | 1.95–2.23 GB | 3.95–5.84 GB（MTP 其中约 5 GB 在划分池子后才释放） | 否 |
| draft KV | 0.16–0.74 GB（4–20 KiB/token） | 0.04–0.16 GB | **是** |
| verify 中间状态（hybrid） | 无 | DSpark/DFlash2 每请求约 0.57 GB；MTP+ReplaySSM 约 0 | 否 |
| target prefill CUDA graph | 0.77 GB | 1.8–2.2 GB | 否 |
| 推测解码的 decode/verify graph | 1.3–2.0 GB（在 static 预算外） | 0.1–0.3 GB | 否 |

结论：**draft KV 在两组模型里都是最小的一项**。即使把它全部回收，A 组也只能补回约 1/4 的容量损失，B 组几乎没有影响。原 proposal 的"draft KV 选择性保留"可以作为相关工作讨论，但不适合作为主线。

## 候选方向（按预期收益/成本排序）

| # | 方向 | 预期收益（来自测量） | 成本 | 备注 |
|---|---|---|---|---|
| O1 | **MTP 共享 embedding/head 的显存记账**：把共享提前到划分池子之前 | B：MTP 并发上限从 4 提到约 15（推算），高并发下吞吐有望回到 plain 水平以上 | 小（改初始化顺序或权重估算） | 是明确的工程缺陷，可以先做、先验证 |
| O2 | **按负载调度推测解码，并把显存还给 target**：高负载时关掉推测，把 draft KV 池、verify 中间状态、graph 显存（甚至 draft 权重，卸载到 host）转给 KV/state 池；低负载时再收回 | A W2 并发 64：DSpark 601 → 最多 984 tok/s（+64%）。B W2 并发 16：MTP 206 → 最多 470（+128%） | 大（需要运行时调整池的大小；可以看看 `--enable-unified-memory` 的多池字节共享能否复用） | **最有研究价值**；可以把原 proposal 改成"前缀缓存与推测解码的联合显存管理"：在 {缓存前缀、运行中请求、推测状态} 三者之间分配显存 |
| O3 | **hybrid 模型上 DSpark/DFlash 的 verify 中间状态压缩**（类似 ReplaySSM） | B：每请求 1.0 → 约 0.45 GB，并发上限 2–3 → 约 6（推算） | 中到大（kernel 和状态管理） | 队友已确认目前 ReplaySSM 不支持 DSpark/DFlash + GDN |
| O4 | adaptive 推测的显存预算：限制候选集合，或按剩余显存决定建几套 graph | 避免默认配置在小显存卡上的 2–3 倍性能退化 | 小 | 偏工程修补 |
| O5 | 报错信息修正：显式指定 mamba 池时，"mem-fraction 调到 X 以上"的提示没把池子算进去 | 可用性 | 很小 | 可作为上游 issue |

## 建议的第二阶段

1. **先做 O1**：改动小、结论清晰，能当作"显存记账影响推测解码服务能力"的第一个实证。验证方法：用 B 组 E1 的探测和 E2 的扫描对比改动前后。
2. **主线做 O2**：设计"负载感知的推测解码与显存再分配"。第一阶段的数据已经给出了收益上界（E3 同容量对照），也给出了切换的触发信号（running 请求数、排队长度、命中率）。原 proposal 的 cost-aware 思想（复用价值 × 重建代价 / 字节）可以用在"显存给谁"这个更大的决策上。
3. O3 视时间而定，可以先做可行性调研。

## 还缺的实验

- W3（多轮/agentic）和 W4（长上下文）还没跑。在长上下文下 draft KV 占比更高，可以检验"draft KV 不重要"这个结论的边界。
- E5 profiling：拆分 W2 高并发下推测解码的 TPOT 构成。
