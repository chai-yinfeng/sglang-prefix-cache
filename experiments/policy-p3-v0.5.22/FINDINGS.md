# Policy 层 P3：前缀分层（2026-10-27）

问题：显存划分修好之后（P2），W2 这种工作集（约 98K token）大于 KV 容量的负载，能不能靠"把前缀卸到 CPU、未命中时取回"（HiCache）把差距补上？另外，P2 的对比只给了 DSpark 打开 capture 后定池大小，这里给 plain 也打开，公平地比一次。

- 环境：Qwen3-8B BF16，RTX 5090，FA4，page 64；
- 所有配置都设置了 `SGLANG_ENABLE_POST_CAPTURE_KV_SIZING=1`；
- HiCache 设置：`direct` + `layer_first`、`write_through`，主机池 12 GB；
- 负载：W2，单次运行；
- 原始数据：`work_dirs/stress-qwen3-8b/runs/p3/`；汇总表：`p3-w2-tiering.csv`（命中率由服务器日志中各点时间窗口内的 prefill 行算出）。

## 结果

单位 tok/s，括号内是相对 plain-pcs 的倍数。

| 配置 | KV（token） | 并发 16 | 并发 64 | 并发 64 命中率 | 并发 64 TTFT 中位数 | 最多同时运行 |
|---|---|---|---|---|---|---|
| plain-pcs | 90,240 | 654 | **1520** | 0.885 | 790 ms | 127 |
| plain-pcs + HiCache | 90,240 | 647 | 1501 | 0.888 | 874 ms | 127 |
| DSpark-pcs | 61,184 | **832（1.27）** | 1065（0.70） | 0.79 | 3920 ms | 83 |
| DSpark-pcs + HiCache | 61,184 | 820 | **1286（0.85）** | **0.875** | 3011 ms | 93 |
| DSpark-pcs + HiCache + LFU | 61,184 | 823 | 1276（0.84） | 0.871 | 3085 ms | 93 |

## 结论

1. **更正 P2**：capture 后定池大小对 plain 同样有效，KV 从 58.7K 涨到 90.2K（+54%），并发 64 吞吐从 1006 涨到 1520。两边都打开后，DSpark 的 KV 仍比 plain 少 32%，W2 并发 64 下仍只有 plain 的 0.70 倍。P2 里的"1.08 倍"是和默认配置的 plain 比出来的。这个开关能回收的是两边共有的余量，推测本身的显存成本（draft 权重约 2 GB、draft KV 每 token 多 14%、推测 graph 约 2.2 GB）一点也没少。
2. **前缀分层把命中率的损失补回来了**：DSpark 打开 HiCache 后，并发 64 的命中率从 0.79 回到 0.875（与 plain 持平），吞吐提高 21%，达到 plain 的 0.85 倍。plain 的 KV 已经放得下大部分工作集，HiCache 对它没有作用。这和 Q6 的代价测量一致：从 CPU 取回 4K 前缀约 42 ms，重算要 320 ms。
3. 剩下 0.85 倍的差距来自**能同时运行的请求数**，而不是命中率：DSpark 最多同时跑 93 个请求，plain 是 127 个，DSpark 的 TTFT 中位数也高出 2.2 秒，都是在排队。HiCache 只能减少重算，增加不了正在运行的请求能用的 KV。要补上这部分，就得在持续高负载时把推测本身的显存还给 KV：释放 draft 权重和推测 graph，再用 VMM 扩池。这是"后期"阶段的工作。
4. 并发 16 时 DSpark 比 plain 快 1.27 倍。
5. LFU 和 LRU 没有差别：W2 的文档长度都一样，"价值密度"排序退化成了按复用频率排序。要体现代价感知的淘汰，需要长度差别大的负载。

## 对 policy 层的含义

- 前缀分层是一个便宜且有效的动作，应该在推测配置里默认打开：它补回了推测因 KV 变小而损失的命中率。
- 推测与否在 W2 上的取舍，本质是"能同时跑的请求数"和"每个请求的 decode 速度"之间的权衡：
  - 并发 16 时推测更好（1.27 倍）；
  - 并发 64 时显存更重要（0.85 倍）。

  这正是按负载切换显存划分的理由，但前提是要有运行时回收推测显存的机制。
